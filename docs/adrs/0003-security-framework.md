# ADR-0003. Вибір системи автентифікації та безпеки

## Статус

Accepted

## Контекст (Context)

У системі TicketWave є кілька типів користувачів з різними правами: покупці, організатори подій, контролери на вході та адміністратори. Також є мобільний застосунок і вебзастосунок (SPA), які звертаються до одного API.

Вимоги, які впливають на рішення:

- **NFR-10** - захист персональних даних (GDPR), увесь трафік через TLS 1.3;
- **NFR-11** - захист від ботів і перекупників (ліміти на акаунт, CAPTCHA);
- **NFR-13** - аудит дій адміністраторів і організаторів;
- користувачі хочуть заходити швидко, наприклад через Google або Apple, без довгої реєстрації;
- для організаторів і адміністраторів потрібен вищий рівень захисту (двофакторна автентифікація);
- писати свою систему автентифікації з нуля - довго і ризиковано, легко зробити помилку в безпеці.

## Рішення (Decision)

Використовувати стандарт **OAuth 2.0 + OpenID Connect (OIDC)** з окремим сервером ідентифікації **Keycloak** (open-source).

Як це працює:

1. Вебзастосунок і мобільний застосунок авторизуються через **Authorization Code Flow з PKCE**.
2. Keycloak видає короткоживучий **Access Token (JWT, 15 хвилин)** і **Refresh Token**.
3. Backend перевіряє підпис JWT (через публічний ключ Keycloak) і ролі користувача: `BUYER`, `ORGANIZER`, `CONTROLLER`, `ADMIN` (RBAC).
4. Підтримується вхід через Google / Apple (Social Login) - Keycloak це вміє з коробки.
5. Для ролей `ORGANIZER` і `ADMIN` обов'язкова двофакторна автентифікація (TOTP).

Додаткові заходи безпеки:

- **API Gateway** робить rate limiting по користувачу і IP (захист від ботів, NFR-11);
- **CAPTCHA** (наприклад, Cloudflare Turnstile або reCAPTCHA) при вході у віртуальну чергу;
- **TLS 1.3** для всього зовнішнього трафіку;
- чутливі персональні дані (телефон, ПІБ) шифруються в БД (AES-256);
- **QR-код квитка** підписується ключем сервера (HMAC-SHA256), щоб квиток не можна було підробити (NFR-12);
- дані банківських карток я не зберігаєю - оплата відбувається на стороні платіжного провайдера;
- усі важливі дії (зміна ціни, скасування події, блокування акаунта) пишуться в **audit log** (NFR-13).

## Розглянуті альтернативи (Alternatives Considered)

- **Альтернатива А: Власна автентифікація (логін/пароль + сесії або власні JWT)**
  - *Переваги:* повний контроль, немає додаткового сервера, простіше на початку.
  - *Недоліки:* треба самостійно реалізувати хешування паролів, відновлення пароля, 2FA, social login, блокування після невдалих спроб; великий ризик помилок у безпеці; багато часу на розробку.
  - *Чому відхилено:* ризиковано з точки зору безпеки та й довго робити.

- **Альтернатива Б: Хмарний сервіс автентифікації (Auth0 / Firebase Authentication / AWS Cognito)**
  - *Переваги:* не треба нічого розгортати і підтримувати; все працює одразу; висока надійність.
  - *Недоліки:* платний при великій кількості користувачів (а на самому старті продажів, можуть бути десятки тисяч активних користувачів); vendor lock-in; дані користувачів зберігаються в сторонньої компанії (питання GDPR).
  - *Чому відхилено:* вартість при зростанні і прив'язка до постачальника. Але це хороший запасний варіант, якщо підтримувати Keycloak буде важко.

- **Альтернатива В: Тільки API-ключі / Basic Auth**
  - *Переваги:* дуже просто.
  - *Недоліки:* не підходить для звичайних користувачів, немає ролей, немає social login і 2FA, ключі легко вкрасти.
  - *Чому відхилено:* не відповідає вимогам безпеки.

## Наслідки (Consequences)

- **Позитивні наслідки:**
  - Використовую стандартні протоколи (OAuth2 / OIDC), тому легко підключити нові клієнти(наприклад, застосунок для контролерів).
  - Не пишу свою автентифікацію - менше ризиків безпеки, вже є 2FA, social login, блокування після невдалих спроб.
  - Backend перевіряє JWT локально, без запиту до Keycloak на кожен виклик - це швидко і не збільшує затримку.
  - Чіткий поділ прав через ролі (RBAC), легко перевіряти в тестах.
  - Rate limiting + CAPTCHA + ліміти на акаунт сильно ускладнюють роботу ботів.

- **Негативні наслідки / Компроміси (Trade-offs):**
  - Keycloak - ще один компонент, який треба розгорнути, оновлювати і моніторити; він досить «важкий» по пам'яті.
  - Якщо Keycloak недоступний, нові користувачі не зможуть увійти (вже авторизовані продовжать працювати до кінця дії токена). Тому Keycloak треба запускати мінімум у 2 екземплярах.
  - JWT не можна миттєво «відкликати» - заблокований користувач може працювати до 15 хвилин. Тому токени короткоживучі, а для критичних дій (тієї ж покупки) додатково перевіряти, чи акаунт не заблокований.
  - CAPTCHA трохи погіршує зручність для звичайних користувачів (Usability), тому доведеться показувати її тільки при вході в чергу, а не на кожній дії.
  - Треба розібратися в OAuth2 / OIDC і налаштуванні Keycloak (і як його підключити до ASP.NET Core та Angular) - це займе час.
