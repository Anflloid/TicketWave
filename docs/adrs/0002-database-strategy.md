# ADR-0002. Вибір стратегії баз даних і зберігання даних

## Статус

Accepted

## Контекст (Context)

У системі TicketWave є кілька видів даних з різними вимогами:

1. **Замовлення, оплати, квитки, статуси місць** - тут найважливіша цілісність даних. Не можна допустити, щоб одне місце продалося двічі (NFR-05), або щоб оплата пройшла, а квиток не створився. Потрібні ACID-транзакції.
2. **Схеми залів** - досить складна вкладена структура (зал → сектори → ряди → місця з координатами для малювання на екрані). Читається дуже часто, змінюється рідко.
3. **Статуси місць під час старту продажів** - тисячі користувачів одночасно дивляться схему залу і хочуть бачити актуальні вільні місця (NFR-01: p95 ≤ 300 ms при 2 000 RPS). Якщо кожен такий запит буде йти в основну БД, вона не витримає.
4. **Віртуальна черга і тимчасові резерви** - дані живуть недовго (хвилини), потрібна дуже швидка робота і автоматичне видалення по таймауту (NFR-06).
5. **Пошук подій** - пошук за назвою, містом, датою.

Також враховано, що бюджет обмежений, а для обраного стеку (ASP.NET Core) є зручна робота з реляційними БД через Entity Framework Core.

## Рішення (Decision)

Обрано **PostgreSQL як основну БД + Redis як кеш і сховище для швидких тимчасових даних**.

**PostgreSQL** використовується для:

- подій, замовлень, оплат, квитків, користувачів;
- статусів місць - запис у таблиці `seats` з полем `status` (FREE, RESERVED, SOLD). Щоб не було подвійного продажу, бронювання робиться атомарним запитом:
  ```sql
  UPDATE seats
  SET status = 'RESERVED', reserved_by = :userId, reserved_until = now() + interval '10 minutes'
  WHERE id = :seatId AND status = 'FREE';
  ```
  Якщо оновлено 0 рядків - місце вже зайняте, і API повертає 409 Conflict. Також на таблиці `tickets` стоїть унікальний індекс на (`event_id`, `seat_id`) як додатковий захист;
- схем залів - зберігати в полі типу **JSONB**, тому окрема документна БД не потрібна;
- пошуку подій на першому етапі - через Full-Text Search у PostgreSQL та індекси.

**Redis** використовується для:

- кешування схеми залу і поточних статусів місць (щоб основна БД не отримувала тисячі однакових запитів);
- віртуальної черги (Sorted Set за часом входу користувача);
- rate limiting (лічильники запитів з TTL);
- зберігання сесій.

Основне джерело правди - тільки PostgreSQL. Redis - допоміжний: якщо дані в Redis пропадуть, їх можна відновити з PostgreSQL.

Для надійності PostgreSQL розгортається в керованому хмарному сервісі з репліками (primary + read replica) і автоматичними бекапами (для RPO ≤ 1 хв за NFR-09).

## Розглянуті альтернативи (Alternatives Considered)

- **Альтернатива А: Тільки MongoDB (NoSQL)**
  - *Переваги:* зручно зберігати схеми залів як документи; гнучка схема даних; добре масштабується горизонтально.
  - *Недоліки:* багатодокументні транзакції є, але вони складніші і повільніші; немає звичних зовнішніх ключів; для фінансових даних (оплати, повернення) реляційна модель надійніша; реляційна модель простіша для навчального проєкту.
  - *Чому відхилено:* для мене головне - цілісність бронювань і оплат, а PostgreSQL дає це простіше. Зберігання схем залу вирішується через JSONB.

- **Альтернатива Б: Тільки PostgreSQL без Redis**
  - *Переваги:* простіше - одна БД, менше компонентів для підтримки.
  - *Недоліки:* під час старту продажів тисячі запитів на схему залу і на чергу йдуть прямо в БД; кількість з'єднань і навантаження на CPU БД різко зростають; складно зробити швидку чергу і rate limiting.
  - *Чому відхилено:* за моєю оцінкою не витримаю NFR-01 і NFR-03 під час піку.

- **Альтернатива В: Polyglot Persistence (PostgreSQL + MongoDB + Redis + Elasticsearch)**
  - *Переваги:* для кожного типу даних найкраща БД; Elasticsearch дає дуже потужний пошук.
  - *Недоліки:* багато різних систем, які треба підтримувати, бекапити і моніторити; треба синхронізувати дані між ними; дорожче; для однієї людини це забагато.
  - *Чому відхилено:* занадто складно для MVP. Elasticsearch можу додати пізніше, якщо пошуку в PostgreSQL буде не вистачати (окремий ADR).

## Наслідки (Consequences)

- **Позитивні наслідки:**
  - ACID-транзакції PostgreSQL + атомарний `UPDATE ... WHERE status = 'FREE'` + унікальний індекс гарантують відсутність подвійного продажу (NFR-05).
  - Redis знімає основне навантаження читання з PostgreSQL під час піку (NFR-01, NFR-03).
  - Автоматичне видалення тимчасових даних за TTL у Redis спрощує реалізацію черги і rate limiting.
  - Всього дві технології зберігання - простіше підтримувати, бекапити і моніторити.

- **Негативні наслідки / Компроміси (Trade-offs):**
  - Дані в кеші Redis можуть на короткий час не збігатися з PostgreSQL (eventual consistency) - користувач може побачити місце вільним, хоча його щойно забронювали. Але остаточна перевірка все одно робиться в PostgreSQL, тому користувач просто отримає «місце вже зайняте».
  - Потрібно правильно інвалідувати кеш після зміни статусу місця, а це додаткова логіка і можливі помилки.
  - Під час старту продажів усі записи (бронювання) все одно йдуть на один primary-сервер PostgreSQL - він може стати «вузьким місцем». Якщо це станеться, буду розглядати секціонування (partitioning) таблиці `seats` по подіях.
  - Redis - ще один компонент, який треба моніторити; якщо він впаде, черга і кеш перестануть працювати (потрібна репліка Redis).
