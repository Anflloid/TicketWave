# 1. Опис системи та матриця стейкхолдерів

## 1.1. Загальний опис системи

**TicketWave** - онлайн-платформа для продажу квитків на концерти, спортивні матчі, театральні вистави та інші події. Організатори створюють подію, завантажують схему залу і ставлять ціни на різні сектори. Покупці заходять на сайт або в мобільний застосунок, обирають подію, дивляться схему залу і вибирають конкретні місця.

Головна особливість нашої системи - це робота під великим навантаженням у момент старту продажів. Коли починається продаж квитків на популярний концерт, за кілька хвилин на сайт можуть зайти десятки тисяч людей одночасно, і всі хочуть купити найкращі місця. Тому система повинна:

- не продати одне й те саме місце двом людям;
- не «падати» під навантаженням;
- не дати перекупникам скупити всі квитки ботами.

## 1.2. Бізнес-цілі

1. Продавати квитки онлайн швидко і без помилок (без подвійного продажу місць).
2. Витримувати пікові навантаження під час старту продажів популярних подій.
3. Зменшити кількість квитків, які скуповують перекупники (боти, масові покупки).
4. Дати організаторам зручний інструмент для створення подій і перегляду статистики продажів.
5. Отримувати дохід з сервісного збору з кожного проданого квитка.

## 1.3. Межі системи (System Scope)

**Входить у систему:**

- каталог подій (пошук, фільтри за містом, датою, категорією);
- інтерактивна схема залу з відображенням вільних / зайнятих місць;
- тимчасове бронювання місця (резерв на 10 хвилин, поки користувач оплачує);
- оформлення замовлення та оплата через зовнішній платіжний сервіс;
- генерація електронного квитка з QR-кодом;
- віртуальна черга при старті продажів популярних подій;
- захист від перекупників (ліміт квитків на акаунт, CAPTCHA, виявлення ботів);
- кабінет організатора (створення події, налаштування схеми залу і цін, статистика);
- повернення квитків;
- сповіщення (user_email, push).

**Не входить у систему (зовнішні системи):**

- платіжний шлюз (наприклад, LiqPay або Stripe) - інтегруюсь тільки з ним;
- поштовий сервіс для розсилки email (наприклад, SendGrid);
- сервіс push-сповіщень (Firebase Cloud Messaging);
- турнікети / сканери на вході - вони тільки зчитують QR-код через ключ API перевірки квитка.

## 1.4. Основні користувачі та функції

| Користувач | Що робить у системі |
|---|---|
| Покупець | Шукає події, вибирає місця, оплачує, отримує квиток, повертає квиток |
| Організатор | Створює подію, завантажує схему залу, задає ціни, дивиться продажі |
| Контролер на вході | Сканує QR-код квитка і перевіряє, чи він дійсний |
| Адміністратор платформи | Модерує події, блокує підозрілі акаунти, налаштовує систему |

## 1.5. Матриця стейкхолдерів (Stakeholders & Concerns) за ISO/IEC/IEEE 42010:2022

| Роль стейкхолдера | Представник | Ключові занепокоєння (Concerns) | Вплив на архітектуру |
|---|---|---|---|
| End User (Покупець) | Клієнт, який купує квиток | Швидко завантажується схема залу (< 1 с), місце не «зникає» під час оплати, зручний інтерфейс, чесний шанс купити квиток без ботів | Вимоги до Latency, Usability, Integrity (немає подвійного продажу), захист від ботів |
| Event Organizer (Організатор) | Концертна агенція, спортивний клуб | Продати всі квитки, бачити статистику продажів у реальному часі, зручно налаштувати схему залу | Вимоги до функціональності кабінету, звітів, до інтеграції з їхніми системами |
| Business Owner | Власник платформи / CEO | Вартість хмарної інфраструктури, швидкий вихід на ринок, репутація (сайт не має падати на старті продажів) | Бюджетні обмеження, вибір хмари, вимоги до Scalability та Availability |
| Developer (Розробник) | Розробник проєкту (проєкт веде одна людина, стек: ASP.NET Core + Angular) | Зрозумілий код, легко додавати нові функції, легко тестувати, не тонути в інфраструктурі | Вимоги до Modularity, Testability, вибір архітектурного стилю |
| DevOps / SysAdmin | Інженер підтримки | Моніторинг, CI/CD, автоматичне масштабування при піках, швидке відновлення після збою | Вимоги до Deployability, Observability, Fault Tolerance, автомасштабування |
| Security Officer | Фахівець з безпеки | Захист персональних і платіжних даних, захист від ботів і DDoS, відповідність GDPR і PCI DSS | Вимоги до OAuth2/OIDC, TLS 1.3, шифрування, аудит-логів, rate limiting |
| Payment Provider | Платіжний сервіс (LiqPay / Stripe) | Коректна інтеграція через API, обробка callback-ів, ми не зберігаємо дані карток | Вимоги до Interoperability, ідемпотентності платежів |
| Ticket Controller (Контролер) | Працівник на вході | Швидка перевірка квитка, робота навіть при поганому інтернеті | Вимоги до швидкості API перевірки, підпис QR-коду для офлайн-перевірки |
