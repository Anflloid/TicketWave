# 2. Специфікація нефункціональних вимог (NFR) за ISO/IEC 25010:2023

У цьому документі описані нефункціональні вимоги до системи TicketWave. Вимоги згруповані за характеристиками якості зі стандарту ISO/IEC 25010:2023. Для кожної вимоги вказана метрика, щоб її можна було перевірити (наприклад, навантажувальним тестом у k6 або JMeter).

Було обрано 6 характеристик якості, які найбільше важливі саме для сервісу продажу квитків: Performance Efficiency, Reliability, Security, Maintainability, Flexibility та Functional Suitability.

## 2.1. Таблиця NFR

| ID | Категорія (ISO 25010) | Підхарактеристика | Конкретизована нефункціональна вимога | Кількісний індикатор / Метрика |
|---|---|---|---|---|
| NFR-01 | Performance Efficiency | Time Behaviour | Завантаження інтерактивної схеми залу з актуальним статусом місць | Latency p95 ≤ 300 ms при навантаженні 2 000 RPS |
| NFR-02 | Performance Efficiency | Time Behaviour | Пошук подій у каталозі | Latency p95 ≤ 200 ms при 1 000 RPS |
| NFR-03 | Performance Efficiency | Capacity | Кількість одночасних користувачів під час старту продажів | Система витримує 50 000 одночасних користувачів у віртуальній черзі і 3 000 RPS на бронювання місць без помилок 5xx |
| NFR-04 | Performance Efficiency | Resource Utilization | Використання ресурсів серверів у піку | CPU ≤ 75%, RAM ≤ 80% на кожному екземплярі сервісу при 3 000 RPS |
| NFR-05 | Functional Suitability | Functional Correctness | Одне місце не може бути продане двічі | 0 випадків подвійного продажу (double booking) у навантажувальному тесті з 10 000 конкурентних запитів на 100 місць |
| NFR-06 | Functional Suitability | Functional Correctness | Тимчасовий резерв місця автоматично знімається, якщо користувач не оплатив | Резерв звільняється не пізніше ніж через 10 хв + 30 с після створення |
| NFR-07 | Reliability | Availability | Доступність системи для покупців | SLA = 99.9% на місяць (простій ≤ 43.8 хв/місяць) |
| NFR-08 | Reliability | Fault Tolerance | Робота при недоступності платіжного шлюзу | Бронювання місць продовжує працювати, оплати ставляться в чергу на повтор; 0% втрачених платежів |
| NFR-09 | Reliability | Recoverability | Відновлення після падіння сервісу | RTO ≤ 15 хв, RPO ≤ 1 хв для бази замовлень |
| NFR-10 | Security | Confidentiality | Захист персональних даних покупців | Персональні дані шифруються в БД (AES-256), увесь трафік - тільки TLS 1.3; дані банківських карток у нас не зберігаються (PCI DSS - на стороні платіжного провайдера) |
| NFR-11 | Security | Authenticity | Захист від ботів і перекупників | Rate limit: не більше 10 запитів на бронювання за хвилину з одного акаунта; ліміт - 4 квитки на одну подію на акаунт; CAPTCHA при вході в чергу |
| NFR-12 | Security | Integrity | QR-код квитка не можна підробити | QR-код містить цифровий підпис (HMAC-SHA256 або ECDSA); 100% підроблених квитків відхиляються при скануванні |
| NFR-13 | Security | Accountability | Логування дій адміністраторів і організаторів | Всі зміни подій, цін і статусів квитків записуються в audit log, логи зберігаються ≥ 1 рік |
| NFR-14 | Maintainability | Testability | Покриття коду автотестами | Покриття модулів Booking, Payment і Ticket юніт-тестами ≥ 75% (xUnit + Coverlet, перевірка в CI) |
| NFR-15 | Maintainability | Modularity | Модулі системи слабо пов'язані | Модулі взаємодіють тільки через публічні інтерфейси, 0 порушень правил залежностей (перевіряється тестами NetArchTest у CI) |
| NFR-16 | Flexibility | Scalability | Горизонтальне масштабування під час піків | Автомасштабування (HPA): новий под додається, якщо CPU > 65% довше 1 хв; новий под готовий приймати трафік ≤ 60 с |
| NFR-17 | Interaction Capability | User Error Protection | Користувач не може випадково купити не те місце | Перед оплатою показується підтвердження з сектором, рядом, місцем і ціною; таймер резерву видно на екрані |

## 2.2. Пояснення до найважливіших вимог

**NFR-03 (Capacity).** Узято 50 000 одночасних користувачів, бо великі концерти в Україні (наприклад, на стадіоні) можуть мати 30-70 тисяч місць, і на старт продажів приходить приблизно стільки ж людей. Щоб сервери не впали, не пускаємо всіх одразу, а ставимо у віртуальну чергу і пропускаємо порціями.

**NFR-05 (немає подвійного продажу).** Це найважливіша вимога для системи. Якщо два покупці отримають квиток на одне місце, буде конфлікт на вході і скарги. Тому потрібно заздалегідь уникнути подібних випадків, навіть під великим конкурентним навантаженням.

**NFR-07 (Availability 99.9%).** Якщо порахувати, 99.9% на місяць - це трохи більше 43 хвилин, коли сайт може не працювати - а це вже критично для системи. Щоб система не падала саме під час старту продажів, логічним та правильним рішенням буде перенести проведення планових робіт вночі, а не в дні старту продажів.

**NFR-11 (захист від ботів).** Без цієї вимоги перекупники за допомогою скриптів скуповують квитки за секунди, а потім перепродують дорожче. Ліміти на акаунт і CAPTCHA не дають 100% захисту, але сильно ускладнюють їм роботу.

## 2.3. Як перевіряти вимоги

| Вимоги | Спосіб перевірки |
|---|---|
| NFR-01 - NFR-04, NFR-16 | Навантажувальне тестування (k6 / JMeter), метрики з Prometheus + Grafana |
| NFR-05, NFR-06 | Інтеграційні тести з паралельними запитами на одне місце |
| NFR-07 - NFR-09 | Моніторинг uptime, тестування відновлення з бекапу, chaos-тести (вимкнення поду) |
| NFR-10 - NFR-13 | Перевірка конфігурації TLS, security-сканування (OWASP ZAP), рев'ю аудит-логів |
| NFR-14, NFR-15 | Звіт покриття Coverlet, тести NetArchTest у CI (GitHub Actions) |
| NFR-17 | Юзабіліті-тестування на 5-7 користувачах |
