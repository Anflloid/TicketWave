# 3. Сценарії якісних атрибутів (Quality Attribute Scenarios)

Кожен сценарій описаний за 6 обов'язковими елементами: Source, Stimulus, Environment, Artifact, Response, Response Measure. Для кожної обраної характеристики якості зроблено по одному сценарію.

---

## QAS-1. Продуктивність під час старту продажів (Performance Efficiency)

| Елемент | Опис |
|---|---|
| **Source (Джерело)** | Зареєстровані покупці, які чекали старту продажів на концерт популярного артиста |
| **Stimulus (Імпульс)** | Після виходу з віртуальної черги покупці одночасно відкривають схему залу і надсилають запити на бронювання місць - 3 000 запитів POST /reservations на секунду |
| **Environment (Середовище)** | Пікове навантаження (Peak Load), перші 15 хвилин після старту продажів |
| **Artifact (Артефакт)** | API Gateway, модуль бронювання (Booking Module), кеш статусів місць (Redis) |
| **Response (Реакція)** | Система перевіряє, чи вільне місце, ставить тимчасовий резерв на 10 хвилин і повертає користувачу підтвердження з таймером. Статус місця на схемі залу в інших користувачів оновлюється |
| **Response Measure (Міра реакції)** | Latency p95 ≤ 300 ms, помилок 5xx < 0.1%, CPU на подах ≤ 75%, оновлення статусу місця в інших користувачів ≤ 2 с |

## QAS-2. Немає подвійного продажу одного місця (Functional Suitability)

| Елемент | Опис |
|---|---|
| **Source (Джерело)** | Два (або більше) покупці в різних браузерах |
| **Stimulus (Імпульс)** | Майже одночасно (різниця < 50 мс) натискають «Забронювати» на одне й те саме місце (Сектор A, ряд 5, місце 12) |
| **Environment (Середовище)** | Пікове навантаження, кілька екземплярів сервісу бронювання працюють паралельно |
| **Artifact (Артефакт)** | Модуль бронювання (Booking Module), база даних PostgreSQL (таблиця seats) |
| **Response (Реакція)** | Тільки один запит успішно ставить резерв (через атомарне оновлення в БД з умовою `status = 'FREE'`). Інші користувачі отримують відповідь 409 Conflict з повідомленням «Місце вже зайняте» і пропозицією обрати інше |
| **Response Measure (Міра реакції)** | 0 випадків подвійного бронювання на 10 000 конкурентних запитів; відповідь «місце зайняте» приходить ≤ 500 ms |

## QAS-3. Відмова платіжного шлюзу (Reliability)

| Елемент | Опис |
|---|---|
| **Source (Джерело)** | Зовнішній платіжний провайдер (LiqPay / Stripe) |
| **Stimulus (Імпульс)** | Платіжний шлюз перестає відповідати (timeout або помилки 503) протягом 5 хвилин |
| **Environment (Середовище)** | Звичайна робота системи (Normal operation), середнє навантаження |
| **Artifact (Артефакт)** | Модуль оплати (Payment Module), черга повідомлень (RabbitMQ) |
| **Response (Реакція)** | Спрацьовує Circuit Breaker, щоб не надсилати нові запити на шлюз, який не працює. Користувач бачить повідомлення «Оплата тимчасово недоступна, ваше місце збережене». Резерв місця автоматично продовжується на 10 хвилин. Запити на перевірку статусу оплат ставляться в чергу і повторюються з exponential backoff. Черговий інженер отримує алерт |
| **Response Measure (Міра реакції)** | 0% втрачених оплат (всі оплати, які пройшли у провайдера, підтверджуються у самій системі після відновлення); сторінки каталогу і схеми залу залишаються доступними 100% часу; алерт приходить ≤ 1 хв |

## QAS-4. Атака ботів-перекупників (Security)

| Елемент | Опис |
|---|---|
| **Source (Джерело)** | Перекупник, який використовує скрипти (боти) з 200 акаунтів і різних IP-адрес |
| **Stimulus (Імпульс)** | Боти масово намагаються стати в чергу і забронювати якнайбільше місць - понад 100 запитів на хвилину з кожного акаунта |
| **Environment (Середовище)** | Старт продажів, пікове навантаження |
| **Artifact (Артефакт)** | API Gateway (rate limiter), модуль віртуальної черги, модуль антибот-перевірки, модуль бронювання |
| **Response (Реакція)** | API Gateway обмежує кількість запитів з одного акаунта і IP (rate limiting). При вході в чергу користувач проходить CAPTCHA. Модуль бронювання не дозволяє купити більше 4 квитків на одну подію на акаунт. Підозрілі акаунти (однакова картка, однакові пристрої) позначаються і блокуються адміністратором. Всі блокування пишуться в audit log |
| **Response Measure (Міра реакції)** | ≥ 95% запитів понад ліміт відхиляються з кодом 429 Too Many Requests; жоден акаунт не має більше 4 квитків на подію; час відповіді для звичайних користувачів не зростає більше ніж на 10% |

## QAS-5. Додавання нового способу оплати (Maintainability)

| Елемент | Опис |
|---|---|
| **Source (Джерело)** | Розробник проєкту |
| **Stimulus (Імпульс)** | Бізнес просить додати новий спосіб оплати - Apple Pay / Google Pay через іншого провайдера |
| **Environment (Середовище)** | Етап розробки (Design time), система вже працює в продакшені |
| **Artifact (Артефакт)** | Модуль оплати (Payment Module), інтерфейс `PaymentGateway` |
| **Response (Реакція)** | Розробник створює новий клас-адаптер, який реалізує інтерфейс `PaymentGateway`, пише для нього юніт-тести і додає конфігурацію. Код модулів бронювання, квитків і каталогу не змінюється |
| **Response Measure (Міра реакції)** | Зміни робляться тільки в модулі Payment (0 змінених файлів в інших модулях); час на реалізацію ≤ 3 робочих дні; покриття нового коду тестами ≥ 80%; усі старі тести проходять |

## QAS-6. Масштабування під час піку (Flexibility) - додатковий сценарій

| Елемент | Опис |
|---|---|
| **Source (Джерело)** | Масовий наплив покупців після анонсу додаткового концерту в соцмережах |
| **Stimulus (Імпульс)** | Навантаження зростає з 200 RPS до 2 500 RPS за 3 хвилини |
| **Environment (Середовище)** | Система працює на мінімальній кількості подів (2 екземпляри) |
| **Artifact (Артефакт)** | Kubernetes кластер, Horizontal Pod Autoscaler, сервіс застосунку |
| **Response (Реакція)** | HPA бачить, що CPU > 65% довше 1 хвилини, і додає нові поди. Load balancer починає розподіляти трафік на нові поди. Коли навантаження падає - зайві поди видаляються |
| **Response Measure (Міра реакції)** | Новий под готовий до роботи ≤ 60 с; під час масштабування помилок 5xx < 0.5%; після спаду навантаження кількість подів повертається до мінімальної ≤ 10 хв |
